## 2. Identity resolution (P1.4) — CONFIRMED

- Normalized (`strip().lower()`) exact email match resolves 29/32 samples and 418/518 evaluation
  requests; the remaining 3 samples (`case_10`, `case_29`, `case_30`) and 100 evaluation requests
  resolve through `user_audit_log.csv` rows with `field_name=email` (`old_value`/`new_value`).
  0 unresolved, 0 ambiguous across all 550 requests.
- `sha256(lower(current_email)) == email_hash` holds for every identity row; historical emails do
  NOT match the current `email_hash` (the hash tracks the current email only).
- Evidence files contain UPPERCASE emails (`CHOI.JIHOON94@GMAIL.COM` in `evidence_03`) → all
  matching must be case-insensitive.
- No snapshot `updated_at` lies after any sample `audit_at` (no future-peek risk in identity joins).
- Historical identifier sets must include audit-log old/new values for `email`, `phone` and
  `email_hash` with `event_time <= audit_at` (cases `case_10`, `case_12`, `case_15`, `case_18`,
  `case_25` show 1–2 field mutations).

## 3. Resource→user linkage (P1.5) — PARTIAL, exceptions listed

Linkage mechanisms observed, in priority order:

1. **Identifier in evidence content** (88/111 golden resources): any current/historical email,
   phone (raw or digit-only), `email_hash`, full name, or `user_id`/`subject_reference`
   /`customer_reference` string of the case's identity graph appears in the same file
   (`captured_at <= audit_at`) as the `resource_id`. Includes `lookup_key=` pairs in
   `resource_lookup_trace_*.log` and handover `identifier_info` in `evidence_03`.
2. **Activity linkage** (14 resources): `LINK_RESOURCE_IDENTITY` events (12 in dataset, e.g.
   `activity_4007` proves `object_19` belongs only to priya.raman@gmail.com) or activity
   `details` containing an identifier.
3. **Primary-account workflow events** (14 resources, all `account_*`): exactly one
   `deletion_worker` `DELETE_RECORD` event per case with `event_time` inside
   `(requested_at, reported_at + ~30 min]`. The event details carry no identifier; the case↔account
   binding is established **only** by this workflow-window correlation (confirmed for cases 01, 02,
   07, 08, 09, 10, 18, 20, 22, 23, 29, 30, 31, 32). This is the intended hook for primary accounts
   that no text evidence mentions.
4. **PDF/PNG content**: `evidence_58` (support attachment `support_001` w/ full PII), `evidence_18`
   (`user_18` statement + `ORD-20261260`), `evidence_27` (finance register rows `user_XX`),
   `evidence_55` (`audit_record_003` ↔ `user_03`), `evidence_42` (customer-reference registry for
   `user_17`), `evidence_37` (Sentinel console, `audit_record_001..006` ↔ `user_03`). PNGs not yet
   machine-extracted (Phase 4 VLM); PDF text extracted with pypdf in `explore_evidence.py`.

Exceptions / deviations:

- **Post-audit-only linkage (5 cases, UNRESOLVED vs strict ≤audit reading):** `audit_record_*` (and
  `account_3960`) for `case_09,23,24,29,30` appear in participant-visible text only in
  `evidence_06` (`structured_service_events_eu_west_20260918.log`, captured 2026-09-18) which is
  AFTER their `audit_at` (09-15/09-16). The golden scope still includes them (INCOMPLETE cases,
  verification steps with empty evidence). Interpretation for Phase 5: audit *scope* may be built
  from case-global linkage information while *state* assertions and citations remain ≤ `audit_at`.
  Marked UNRESOLVED — do not hardcode; validate in Phase 6 convergence.
- `case_04` `account_004`: no participant-visible text linkage at all; likely PNG
  (`evidence_04` account console, captured 09-26 > audit 09-07 → NOT eligible) → flagged for
  manual/VLM review; candidate mechanism: implicit identity of `account_%03d` numbering for

- `case_12` `analytics_9914`: linked via **SHA-256 of the HISTORICAL email**

## 5. Evidence-citation rule (P1.7) — CONFIRMED 71/75 + scope rule for 4

- Every citation has `captured_at <= audit_at` (see §6).
- 71/75 cited files (a) mention the step's `resource_id` and (b) are the LATEST eligible file
  mentioning it. The 4 exceptions are ABSENT-proofs: `case_01/02/04` cite `evidence_54` and
  `case_31` cites `evidence_51` for accounts that the file does NOT contain.
- **Citation selection rule (adopted):** for PRESENT/EXPOSED/ACTIVE findings and all COMPLETE
  verifications, cite the latest eligible evidence that *contains* the resource and encodes its
  state; for ABSENT proofs, cite the latest eligible file whose `snapshot_scope`/collection
  *covers the system* and in which the resource is missing (dedicated replicas and snapshot
  bundles serve this role). Each case cites a single evidence id for all of its cited steps
  except `case_04` (two systems proved by two different documents).
- INCOMPLETE verification steps and ALL remediation steps use `evidence_id=""` (77+41 steps).

## 8. Policy edge cases (P1.8)

a) **`case_12 analytics_9914` DELETE vs ANONYMIZE:** the readback line in `evidence_01` shows
   `email_opt_in=true` with `correlation_key = sha256(historical email)`. Hypothesis (PARTIAL):
   an analytics-platform record carrying a marketing opt-in flag is categorised
   `MARKETING_PROFILE` (rule_10 DELETE) rather than `ANALYTICS_PROFILE` (rule_07 ANONYMIZE);
   all other sample analytics resources verify ANONYMIZED and lack the opt-in flag.
   Phase 5 must confirm on the full dataset; treat as rule candidate, not truth.
b) **Compliant flows/backups in COMPLETE verifications:** yes when the user's inventory contains
   them (`case_26/27/28` include `VERIFY_DATA_FLOW_DISABLED`/`VERIFY_RESTORE_BLOCKED` with
   evidence); cases whose users have no connector/backup resource list none (`case_01..04,21`).
c) **Tombstones:** `identity_service` `deleted_customer_references` rows with `subject_reference`
   = user and all direct identifiers null ⇒ REDACTED; leaked name/email/phone ⇒ violation with
   `REPORT_EXPOSED_PII` + `REDACT_RECORD` (`case_31` shows the compliant shape).
d) **SUPPORT_MESSAGE vs SUPPORT_ATTACHMENT:** attachments are proven by support documents/PDFs
   (e.g. `evidence_58` for `support_001`, single-subject ⇒ rule_06 DELETE; `case_07` golden uses
   `REPORT_REMAINING_RECORD`+`DELETE_RECORD`); message records with shared context use REDACT
   (`case_11 support_864`). `LINK_RESOURCE_IDENTITY` phrasing "belongs only to <email>" marks
   single-subject attachments (rule_06) vs shared context (rule_05).
e) **SECURITY_AUDIT_LOG retention:** `security_audit_events`/`security_audit_records` rows carry
   `retention_until` in inventory SQL/readbacks and the signed journal (`evidence_55`,
   retain-until 2027) ⇒ RETAIN ⇒ verification `VERIFY_RECORD_PRESENT`; no sample requires deleting
   an in-window audit record.
